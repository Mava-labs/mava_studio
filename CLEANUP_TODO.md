## Phase 0 — Decisions needed before touching code

### 0.1 Vue Vapor — ✅ DECIDED: scope to canvas only
Vapor's whole point — compiled fine-grained reactivity instead of vDOM diffing — is a legitimate fit for the one place in this app that actually has a performance problem: many discrete, frequently-mutated elements on the canvas (drag, resize, live style edits). That's a real, defensible reason to reach for it, not a fashion choice.

The risk is that Vapor is currently applied to *every* component (`<script setup lang="ts" vapor>` appears in `AppHeader.vue`, `SideNav.vue`, `App.vue`, the RightPanel, etc.) — chrome that has zero performance case for it. You're paying the full risk premium of a beta framework mode (unstable API, thin ecosystem/tooling, and it's already forced workarounds: the manual push-based undo stack instead of reactive history, the imperative `render-bridge.ts`/`resolver.ts` renderer that already replaced an earlier version once, hand-rolled `getElementById`/`classList` menus in `AppHeader.vue` instead of reactive state) across 100% of the surface area, for a payoff concentrated in maybe 10% of it.

**My recommendation:** keep Vapor for the canvas/stage rendering path (`createMode.vue`, `render-bridge.ts`, `EditorOverlay.vue`) where it's earning its keep, and drop the `vapor` attribute from chrome components (menus, panels, dialogs, terminal) where standard Vue 3 reactivity is simpler, better-documented, and won't break under you on a beta bump. Vue 3.6 supports this mixed mode per-component already — this isn't a rewrite, just dialing back scope on files that don't need it. Worth a short spike to confirm mixed-mode works cleanly with your Pinia stores before committing.

**Execution note:** do this incrementally, file by file, starting with whatever we touch next anyway (e.g. the PropertiesPanel rebuild in 0.3 is a natural first test case — rebuild those panels as plain Vue 3, non-vapor, and confirm they coexist cleanly with the vapor canvas before rolling the change out further). Don't do a mechanical sweep across the whole `src/` tree in one pass — too easy to break something silently on a beta API surface.

### 0.3 PropertiesPanel — ✅ DECIDED: curated panels are primary, generic system retired to a proper GeometryPanel
You were right that something's off, and I found the concrete cause. There are **two parallel systems** fighting for the same panel:

1. **Curated, hand-built panels** — `LayoutPanel.vue` (X/Y/W/H with steppers), `TransformPanel.vue` (scale/rotate), `EffectsPanel.vue` (opacity/blur), `TextPanel.vue` (font/weight/size/color/align/bold/italic/underline/strikethrough/line-height/letter-spacing), `FillStroke.vue`, `RadiusPanel.vue` (per-corner + link toggle), `PaddingPanel.vue` (per-side + link toggle). These are genuinely close to your reference screenshot already — same dark theme, steppers, lock/link icons, segmented align buttons.
2. **A generic, auto-generated system** — `styleMatrix.ts` maps element type → property-group IDs, and `GroupRenderer.vue` renders each group by guessing a control type from the property name via regex (`/color|fill/i` → color picker, `/width|height/i` → number, etc.), with labels auto-generated by capitalizing the raw prop name.

In `StylePanel.vue`, the routing is:
```
groups = getGroupsForElementType(el.type)      // ALWAYS returns something —
                                                 // styleMatrix.ts has a non-empty
                                                 // fallback for unknown types
<template v-if="groups.length">  ...renders via generic GroupRenderer...
<template v-else>  <LayoutPanel/><TransformPanel/><EffectsPanel/>  </template>
```
Because `getGroupsForElementType` always returns a non-empty array (there's a hardcoded fallback), **the `v-else` branch can never fire.** `LayoutPanel`, `TransformPanel`, and `EffectsPanel` are imported into `StylePanel.vue` but structurally unreachable. `TextPanel`, `FillStroke`, `RadiusPanel`, and `PaddingPanel` are worse off — they're not even imported into `StylePanel.vue` at all. What actually renders today, for every element, is the generic auto-labeled fallback — which is why it doesn't look like your reference even though the components that *would* match it already exist and mostly work.

It's not a clean "delete the bad one" situation, though — `GroupRenderer.vue` also hosts `SvgStrokeControl`/`SvgFillControl`/`SvgGeometryControl` for SVG shape properties (rect/circle/ellipse fill, stroke, geometry) that the curated panels don't fully cover (`FillStroke.vue` only branches on `el.kind === 'svg'` for fill/stroke, nothing handles `cx/cy/rx/ry/points` geometry at all today). So the real fix is reconciliation, not a one-line delete: make the curated panels the primary path for the properties they cover, keep (or migrate) the SVG-specific controls as their true fallback, and finish a geometry panel for shapes rather than routing shapes through the generic labeler.

**Execution note:** you flagged the panels themselves need a visual refactor pass, not just a routing fix — the reference image has details today's curated panels don't fully match yet (icon-prefixed fill/stroke rows, Auto/Fixed width-height sizing toggles, a top icon toolbar). Full scope lands in Phase 3 below.

### 0.4 CF Builder ecosystem — ✅ DECIDED: real `.mcf` import is in scope. Also: studied CF Builder's actual crypto code, and it changes the plan
I read `useCfMapperStore.ts`'s `loadFromDisk()`: it opens a file picker filtered to `extensions: ['json']` and calls `readTextFile()` — a plain-text read — then hands the raw string to `cfStore.importFramework()` as JSON. Per your brief, CF Builder's actual published output (`.mcf`) is AES-256-GCM encrypted, RSA-OAEP key-wrapped, and Ed25519-signed — not readable as plain text at all, and `mava_studio`'s `src-tauri/Cargo.toml` has none of those crypto dependencies (no `aes-gcm`, `rsa`, or `ed25519-dalek` — that stack currently only lives in `mava-registry`, which per your description is BitPulse Registry). So today's CF import path works only against hand-authored test JSON, not anything CF Builder actually produces. This was invisible until you mentioned CF Builder's real format — good catch on your end surfacing it.

Confirmed — JSON-only was an oversight, not intentional. I read `cf-builder/src-tauri/src/cf/crypto.rs` and `persistence.rs` to get the real format instead of guessing, and there's good news: **the read-side logic Mava Studio needs already exists, written and working, inside CF Builder.**

Exact `.mcf` layout (from `persistence.rs`'s own doc comment):
```
[8]  magic "MAVA_MCF"
[4]  header_len (LE u32)
[N]  protobuf FileHeader
[M]  protobuf McfFile { wrapped_key, nonce, ciphertext, signature, framework_id, publisher_id, license_required }
```
Publish flow: generate a random 32-byte AES key → encrypt the framework proto with it (AES-256-GCM) → wrap that key with **Mava Studio's** RSA-OAEP public key → sign `header ++ wrapped_key ++ nonce ++ ciphertext` with Ed25519 → write to disk. `persistence.rs` even has a comment: *"Called by Mava Studio, not CF Builder. Included here so the verification logic is shared"* above `read_mcf_header`, `verify_mcf_signature`, and `decrypt_mcf` — meaning whoever built CF Builder already wrote Mava Studio's reader for you, it's just sitting in the wrong repo.

**Recommendation, in the spirit of "simplified, direct-to-the-point":** don't reimplement this in `mava_studio` from scratch. Pull `crypto.rs` + the read-side of `persistence.rs` (plus the shared `FileHeader`/`McfFile` proto messages) into a small shared Rust crate both apps depend on. Right now CF Builder and Mava Studio are two unrelated Cargo projects that would otherwise end up with two hand-maintained copies of security-critical crypto code — a fix or a format change in one wouldn't propagate to the other. A shared crate (or a Cargo workspace across `cf-builder/src-tauri`, `mava_studio/src-tauri`, and `mava-registry`) is less code overall, not more — consistent with your stated goal.

**One real open question, not yet decided anywhere I can see in the code:** `crypto.rs`'s doc comment on `decrypt_mcf` says the wrapped CF key gets unwrapped *"either locally or via the licensing server."* That's two different architectures:
- **(a) Local custody** — Mava Studio ships holding the RSA private key on every install and unwraps offline. Simpler, works offline, but means a private key lives inside a distributed desktop binary — not great security practice for something meant to gate access to licensed content.
- **(b) Server-side unwrap** — Mava Studio sends the `wrapped_key` to `mava-registry`'s licensing endpoint (which already exists — `licensing/handlers.rs`, `licensing/models.rs`), the server checks the license and returns the unwrapped key. Matches the `license_required: "key"` field already present in `McfFile`, and the private key never leaves the server. Requires network access to open a `.mcf` for the first time (could still cache the unwrapped key locally after).

I'd lean toward (b) given the licensing infrastructure already exists in `mava-registry` and (a) has a real key-custody weakness, but this is a product/security call, not just an engineering one — your read?

### D1. Two disconnected "display" models — ✅ RESOLVED (2026-07-08, same-day follow-up)
You reported flex/grid/block edits didn't apply at all (tested on a div containing a button and another div) — this was the practical consequence of the duplication described below, and worse than I'd realized when I first flagged it: `resolveContainerStyle()` didn't just leave `ContainerElement.display`'s richer config unwired, it **actively overrode** `css.display` with `el.display.mode` *after* `resolveBaseStyle` had already set it correctly from `layout.mode` — so `Layout.mode` (what the new Auto Layout panel edits) had **zero** effect on any container, ever, not just an incomplete one. Fixed: removed the override entirely; `resolveLayout`/`resolveDisplay` (driven by `layout.mode`) is now the sole authority on `display` for every element kind, containers included. `ContainerElement.display` + `FlexDisplay`/`GridDisplay` are still on the type and still constructed by `buildContainer()` (defaults to `{mode:'block'}`) but nothing reads them anymore — fully orphaned now, not half-wired. Formal removal from the type/builder is still worth doing as a follow-up cleanup, just no longer urgent since it can't cause incorrect behavior anymore.

<details><summary>Original finding (superseded by the fix above)</summary>


Found while wiring the Auto Layout panel: there are **two separate, unconnected systems** describing how a container arranges its children.
- `Layout.mode: 'flow'|'flex'|'grid'` + `direction`/`justify`/`align`/`wrap`/`gap`/`columns`, sitting on every `BaseElement`. **Already fully wired** — `resolveDisplay()` in resolver.ts reads all of these and produces correct CSS for any element.
- `ContainerElement.display: {mode:'block'}|{mode:'flex',config:FlexDisplay}|{mode:'grid',config:GridDisplay}` (`FlexDisplay`/`GridDisplay` defined in `types/project.ts`, richer — `grow`, `spacing`, `alignItems`, `justifyContent`, direction with reverse variants). **Only half-wired** — `resolveContainerStyle()` reads `display.mode` to set `css.display`, but never touches `display.config` at all, so none of `FlexDisplay`/`GridDisplay`'s actual fields (grow, spacing, alignItems, justifyContent, wrap, gap) ever reach CSS. Setting these today would silently do nothing.

I built the new Auto Layout panel against `Layout`, since it's the one that actually renders. **Recommendation:** formally deprecate `ContainerElement.display` + `FlexDisplay`/`GridDisplay` and delete `resolveContainerStyle`'s partial handling of it, rather than finishing the wiring on both — one model is simpler and it already works end to end. If there's a reason `FlexDisplay`/`GridDisplay`'s richer shape (grow, spacing enum, reverse directions) is needed later, worth deciding now rather than after more code builds on either side.

### Code-quality audit of the variables/bindings implementation (2026-07-09)

User asked directly whether this was solid or "junior" work. Assessment: the *design* is genuinely good (typed variable defs, a real transform-compatibility matrix instead of silent coercion, list/object bindings as first-class cases). The *implementation* has real bugs — worth fixing as part of wiring bindings into the element/render pipeline (not deferred further, since we're about to touch this code anyway):

1. **`updateVariable()` resets a variable's live value on every rename keystroke.** `VariablesRegistry.vue`'s name `<input>` calls `updateVariable(oldName, {name: nextName})` on `@input` (i.e. per character typed). The store's rename path is delete-old-key-then-recreate-new-key-seeded-from-`defaultValue` — it never carries the old live value forward. Once bindings are live, renaming a variable someone has been interacting with will snap its value back to default, repeatedly, mid-typing. Fix: capture the old value before delete, seed the new key with it instead of `defaultValue`.
2. **`applyWriteTransform`'s `'toBoolean'` case doesn't actually invert.** The `toString`/`toNumber`/`negate` write-cases correctly convert back toward the source variable's real type; `toBoolean` just re-coerces to boolean again. Since `toBoolean` is only compatible with string/number-typed variables (per `TRANSFORM_COMPATIBILITY`), any two-way binding using it will fail `setVar`'s type check on every single write.
3. **Scope-transition cleanup is one-directional.** `upsertVariable` deletes stale `globalVars` entries on a global→page transition but not the reverse — page→global leaves dangling copies in every page's `pageVars`.
4. **`twoWayMap` keys collide across sections.** `resolveBindings()` returns two-way bindings keyed by leaf property name only (e.g. `'value'`), not the full path (`'attributes.value'` vs `'style.value'`) — two two-way bindings with the same leaf name in different sections on the same element will silently overwrite each other in the map, and the section info needed to correctly wire the handler is lost entirely.
5. **`parseJsExpression()` in `VariablesRegistry.vue` uses `new Function(...)`** to parse list/object default-value literals — an eval-equivalent. Low real-world risk today (single local user editing their own project), but a genuine code-execution risk the moment project files can be shared/imported across the ecosystem, which is the entire point of CF Builder/Registry existing. Cheap to swap for a real, safe literal parser now; expensive to remember once sharing is live.

Not yet fixed — queued as step 1 of the Properties/bindings phase (see "Recommended next steps" in `CLAUDE.md`).

## Phase 3.23 — Direct-grab: reaching nested elements without the ring blocking them — ✅ DONE (2026-07-09)

You reported "hard almost impossible to get hold of contained elements" — a real bug, and a bigger one than it first looked. Two compounding causes:

1. **No selection yet.** Grabbing a never-selected nested element (a button inside a div) required two separate clicks before a drag could even begin: click once → three-tier resolution always lands on the root container first; click again → drills into the child; only *then* does the child have its own selection ring for a third gesture to grab. Three interactions to move one button.
2. **The bigger one: the selection ring itself was the blocker.** Once *any* container was selected, its ring — `pointer-events: auto` across its *entire* bounding rectangle (that's how it caught `@pointerdown` for dragging) — sat on top of everything inside it, including every nested child. So with a container selected, a click anywhere inside its box hit the ring first, not the child underneath. This is almost certainly what you were actually running into most of the time, since after any single click something is generally already selected.

**Fix, in two parts:**

- **`useElementReorder.ts`'s `startReorder` and `useElementDragResize.ts`'s `startDrag`** both gained an optional `onCommit?: () => void` callback, fired exactly once — when the drag threshold is crossed, i.e. the gesture is confirmed to be a drag and not a click. `startDrag` didn't have arming/threshold logic at all before this (it was only ever called from an already-selected ring, so "is this a drag" was assumed); it now arms the same way `startReorder` already did.
- **`createMode.vue`** gained a new `handleStagePointerDown`, delegated on the stage root (same `[data-eid]`-walking `resolveClickIds()` the click handler already used). It resolves the deepest element literally under the pointer and starts a drag/reorder on *that* directly — bypassing the three-tier click-drill entirely, since a press-and-drag gesture already conveys unambiguous intent about which element is meant, unlike a plain click where the drill-down precision is actually wanted. `onCommit` applies the resulting selection change (`selectOnly`, or keeps the existing selection if you grabbed a member of an active multi-select) and sets a `suppressNextClick` flag so the click handler that still fires on pointerup doesn't re-run its own (now stale) resolution on top.
- **`EditorOverlay.vue`'s selection ring is now purely visual** (`pointer-events: none`) — the `ring--draggable` class, its `@pointerdown="onDragStart"`, and the `onDragStart` function itself are gone. All drag initiation goes through `handleStagePointerDown` now, for both a first-time grab and re-grabbing an already-selected element, unifying what used to be two separate code paths (ring-driven vs none) into one. Resize handles are unaffected — they're small and sit at the box's corners/edges, not over its interior, so they don't have the occlusion problem.

## Phase 3.42 — Image sizing explanation + hint, images unselectable (native drag) — ✅ DONE (2026-07-09)

## Phase 3.53 — Named triggers made genuinely global across documents — ✅ DONE (2026-07-09)

- **Runtime**: `activateDslTriggers()` now creates one shared `namedTriggerRegistry: Map<string, () => Promise<void>>` per activation batch and threads it through every document's `activateDslTrigger()` call → `buildTriggerContext()` → injected as `__namedTriggers`. ## Phase 3.59 — Reactivity made granular; two-way bindings wired end to end — ✅ DONE (2026-07-09)

You flagged reactivity as the thing to get right: everything that references an author/system variable (element props via bindings, triggers, scripts) should reactively respond. I audited the actual pipeline (`resolver.ts`, `bindings.ts`, `render-bridge.ts`, `context.ts`) rather than assuming, and found a mix — some genuinely reactive, one correctness gap, one perf/UX problem that blocked two-way from ever being usable.

**What was already sound** (verified, not assumed): variable reads inside `resolveBindings()` hit real Vue `reactive()` state and were tracked, so one-way bindings *did* update; `variable.change` DSL triggers and scripts' `project.watch()` both use real `watch()`. Trigger `when <cond>` reading `__var[...]` evaluates once when the event fires — correct by design, not a bug.

**Problem 1 — the update was a full subtree teardown+rebuild, not a patch.** `mountElement()` wrapped resolve + DOM-build in one `watchEffect`, and the inner per-property effects (`stopStyle`/`stopProps`) captured *snapshots* with no reactive deps — so they ran once and were dead; the only thing providing reactivity was the outer effect, which rebuilt the whole subtree on any bound-variable change. For a two-way `<input>` that means the node — and its focus, caret, selection — is destroyed and recreated on every keystroke, which makes write-back unusable. This is a sibling of the already-logged Phase 3.24 finding, but on the variable-change path specifically (variable changes are the one reactive source that does NOT go through `commitPageToCache` → createMode's full remount; everything structural does).

**Rewrote `render-bridge.ts`** around a per-node model: each element node is built once and owns fine-grained effects (`computed(resolveElement)` feeding separate text / attrs / style `watchEffect`s) that re-resolve and patch in place. The DOM node (and native input state) survives variable changes. One `effectScope` per `mountElement` owns every effect + listener in the subtree, so cleanup is a single `scope.stop()` — replacing the hand-threaded `cleanups` array. Structural changes still come exclusively through createMode/PreviewApp's remount (raw element is immutable within a mount), so no structural reactivity is lost. Component elements keep re-create-on-change semantics (a Vue component's props can't be patched from outside), now scoped to just the component node instead of the whole subtree, with an `onReplace` callback so a root-level component that swaps itself still gets removed correctly on cleanup.

**Problem 2 — two-way bindings and list/repeat were computed but discarded.** `resolveBindings()` builds `twoWayMap` and `repeatList`, but `resolveElementBindings()` only ever destructured `patch` — the other two were dead. And there was no UI to create either (the BindingsPanel hint even admitted write-back "isn't wired yet").

**Two-way, wired end to end** (now that granularity makes it viable — no focus loss): runtime `wireTwoWayBindings()` in render-bridge attaches `input`/`change` listeners that read the control's live value, coerce to the variable's type, apply the write transform, and `setVar()` — cleaned up via `onScopeDispose`. UI: `BindingsPanel.vue` gained a bindable **Value** field (text/textarea/select) and **Checked** field (checkbox/radio), each with a `⇄` two-way toggle that stamps `binding.twoWay` + a write transform; hint updated. Read direction (variable → control) already flows through the normal patch path, so a two-way binding is just a one-way binding + `twoWay: true` + the write listener.

**List/repeat — deliberately NOT built, flagged instead.** `repeatList` (a list variable bound to `children`) has no per-item scope anywhere in the model — repeated children would all be identical — and no authoring surface creates a `children` binding. Building it blind would be guessing at the feature design. Documented in `resolver.ts` (at the `resolveBindings` consumption point) and here as needing a design pass, not a wiring pass.

**Known runtime caveats to check when smoke-testing** (can't verify here): (1) two-way text inputs — Vue's value patching should skip re-assigning an identical string so the caret doesn't jump, but confirm mid-string edits don't jitter; (2) the three patch effects each re-resolve on a change (one `computed`, so one resolve, three cheap DOM applies) — fine, but watch for redundant `terminal.error` spam if a binding references an undefined variable; (3) `<select>` resolver-generated `<option>`s are a static snapshot (no surface binds them) — noted in code as the spot to make reactive if that changes.

**Verified by type-check** — `npx vue-tsc --noEmit`: 22, zero new errors. **Verified by `cargo check`** — untouched, clean. **Not runtime-verified** — smoke test: bind a text input's Value to a string variable with `⇄` on, open Preview, type into it and confirm the variable updates (e.g. via another element one-way-bound to the same variable reflecting live) *without* the input losing focus per keystroke; toggle `⇄` off and confirm it becomes display-only.

Studied the whole component surface before building. **Verdict: thoroughly scaffolded, not wired, and instance rendering is broken — it's effectively greenfield behind a facade.**

**What exists (real):**
- **Data model, solid:** `ComponentDefinition` (`projectMetadata.ts` — id, name, version, `source: 'local'|'marketplace'`, `marketplaceRef`, `rootIds`, `elementsById`, `props: ComponentPropSchema[]`, timestamps) and `ComponentElement` instance (`types/element.ts` — `componentId`, `children`, `props`, `slots`, plus `cf_proof` for CF evidence demands). **What's missing / broken:**
1. **No creation UI** — `addComponent` is called from *nowhere*; `NavAssociates.vue` still says "Components panel placeholder." Can't make a component.
2. **No instantiation** — no way to place a component instance on a page.
3. **Component-editor tabs aren't rendered** — `useComponentEditor` is never called by any UI, and `createMode.vue` only renders `page.rootIds` and `provide('componentLibrary', computed(() => ({})))` — an *empty* library. Opening a component tab would show nothing.

5. **Persistence is a lossy stopgap** — `_snapshot` stores only `elementsById[rootIds[0]]` (the *root* element); `_hydrate` rebuilds via `_elementToComponentDef` into a minimal def (`rootIds:[el.id]`, `props:[]`). 6. **No prop-schema authoring** — you can edit instance prop *values*, but there's no UI to *declare* a component's props.

**Open design decisions (need your call before building):**
- **A. Instance rendering model** — (a) *expand-from-definition*: an instance renders the definition's tree live, so editing the definition updates every instance (true components; the point of templating), or (b) *inline copy*: instantiating copies the tree into the page. The `ComponentElement` having both `componentId` *and* `children`/`slots` is ambiguous between these. Recommend (a).
- **B. Prop/slot substitution** — how a prop value flows into the definition's tree (a binding-to-prop inside the definition, analogous to the repeat `item` binding from Phase 3.65) and how `slots` inject instance-provided children into named holes.
- **C. Persistence** — needs a real full-`ComponentDefinition` round-trip; sits in the same territory as the Phase 4 proto/Rust work. Could be TS-only first (componentLibrary is a JSON blob) with a Rust verify.

**Proposed build sequence (foundation-first):** 1) real persistence round-trip (else nothing survives), 2) instance rendering = expand-from-definition + prop substitution, 3) "create component from selection" + a real Components panel, 4) wire component-editor tabs into the canvas, 5) prop-schema authoring, 6) instantiation (insert/drag from the panel). Steps 1–2 are the foundation; everything else is UI on top.

**Decisions (2026-07-11):** A = **expand-from-definition**. C = **full round-trip**. B = deferred to my proposal (see Phase 3.72 sketch below).

## Phase 3.72 — templating step 2: instance rendering + prop substitution — ✅ DONE (2026-07-11), engine-level

B settled as I proposed: one "context threading" mechanism shared by repeat items and component props.

- **`RenderScope` bundle** — the repeat feature threaded `itemContext?: unknown` positionally through `resolveElement`/`resolveBindings`/`buildElementNode`. ## Phase 4 — Cross-repo / CF ecosystem alignment

**✅ DECIDED: server-side unwrap.** Mava Studio sends the `.mcf`'s `wrapped_key` to `mava-registry`'s licensing endpoint; the registry validates the license and hands back a key Mava Studio can use — private key never touches the desktop app.

But look at what it returns:
```rust
let wrapped_cf_key_b64 = B64.encode(&candidate.wrapped_cf_key);
Ok(Json(ValidateLicenseResponse { valid: true, error_message: String::new(),
    wrapped_cf_key: Some(wrapped_cf_key_b64) }))
```
It hands back the **still-wrapped** key (`wrapped_cf_key`, fetched from its own `framework_versions` table) — not an unwrapped, usable AES key. Confirmed why: `mava-registry/Cargo.toml` has no `rsa` crate at all. The endpoint can validate a license, but it structurally cannot perform the RSA-OAEP unwrap yet — that step doesn't exist anywhere in the current code, on either side. Good that we checked before assuming "server-side unwrap" was already done; it's designed for that shape but not finished.

To actually land the decision you made:
